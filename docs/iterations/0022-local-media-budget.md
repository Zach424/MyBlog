# Iteration 0022：本地媒体预算与发布门禁

## 1. 范围与成功标准

项目继续服务同一目标：作者能从网页或 Obsidian 独立发布可信、可维护的技术内容。上一轮全局复盘确认附件虽已能稳定归档，但任何带图片后缀的文件都可进入 Git，5 MiB 的 Studio 单点限制也无法约束 Obsidian 和普通 Git 提交。本轮单一任务是建立不依赖外部服务的本地媒体契约。

成功标准：图片必须真实可解码、扩展名匹配格式，并满足统一体积/尺寸/动图预算；Obsidian 检查在修改文件前给出可操作摘要，正式发布复用相同检查；Studio 的选择器上限一致；直接 Git 提交仍会被 Next 构建门拦截；Windows 校验后可以立即移动文件；失败不会留下演练内容。

回滚边界包括 Sharp 直接依赖、共享媒体策略、仓库扫描器、Next 配置、Studio 体积设置、Obsidian 发布脚本、测试与文档。不改变现有内容 schema、页面视觉、Vercel/GitHub/OAuth 配置，也不接入图床或自动改写作者原图。

## 2. 项目结构状态

- `lib/media-policy.ts`：媒体预算、扩展名/真实格式映射、Sharp 元数据检查和人类可读摘要；
- `build/validate-media.ts`：递归扫描 `public/uploads`，拒绝链接、非图片和策略违规；全新检出尚无上传目录时视为合法空仓库；
- `scripts/publish-note.mjs`：附件移动前执行检查，`--check-only` 输出逐图证据；
- `next.config.ts`：启动/构建时并行执行内容与媒体仓库校验；
- `studio/config.mjs`：封面选择器最大文件体积从 5 MiB 对齐为 3 MiB；
- `tests/media-policy.test.mjs`：覆盖合法图片、格式伪装、损坏、体积、尺寸和递归扫描；
- `package.json` / `package-lock.json`：把 `sharp@0.35.3` 从 Next 间接依赖提升为明确生产依赖；
- 阅读页面、Markdown 组件、内容文件和公开 URL 本轮不变。

## 3. 设计内容

本轮没有新增页面或视觉组件。作者侧的设计重点是“在不可逆移动之前给足证据”：检查摘要按 `实际格式 · 宽×高 · 帧数 · 体积` 排列，紧跟附件源路径和归档目标，正常图片一行即可判断，错误消息则包含当前值、预算和下一动作。

选择拒绝而不是静默压缩。技术博客图片常承担截图证据、代码可读性和视觉差异比较；后台擅自重编码会改变证据。当前门禁告诉作者裁切、缩放或转为 AVIF/WebP，原文件变更仍由作者确认。自动派生需在以后以保留原件、可重现输出和 Markdown 响应式渲染为独立方案设计。

## 4. 使用的技术

- Sharp 0.35.3 / libvips：读取真实图片格式、方向后尺寸、页数与帧高；
- Node.js `fs/promises`、`path`：普通文件检查、确定性递归和跨平台相对路径；
- TypeScript：只读预算常量、检查结果类型和受支持扩展名映射；
- Next.js 16.3 异步配置：构建前并行执行内容与媒体完整性门；
- Decap CMS：浏览器文件选择阶段的 `max_file_size` 早期反馈；
- Node test：动态生成最小图片，避免把二进制 fixture 永久加入仓库；
- 真实 Obsidian 发布脚本：检查模式和完整“生成内容 → 移动附件 → 全量质量门”演练；
- 本地 Next.js 16.3 配置文档：确认异步 `next.config.ts` 能在返回配置前执行仓库校验。

## 5. 实现的功能

- 只接受 PNG、JPEG、WebP、GIF 和 AVIF；SVG 继续明确拒绝；
- 文件必须能被 Sharp 解码，损坏图片无法进入发布或构建；
- `.jpg`/`.jpeg` 必须解码为 JPEG，`.avif` 对应 Sharp 的 HEIF/AV1 格式标识，其余扩展名也必须匹配；
- 单文件不超过 3 MiB；
- 单帧宽和高各不超过 2560 px；
- 单帧不超过 800 万像素；
- 动图的 `宽 × 单帧高 × 帧数` 不超过 8000 万像素；
- Obsidian `--check-only` 逐张报告格式、宽高、可选帧数和 MiB；
- 正式 Obsidian 发布在写内容、删除草稿和移动文件前完成全部媒体检查；
- Studio 封面选择器先阻止超过 3 MiB 的文件；
- `next dev`、`next build`、本地检查和 GitHub Quality Gate 扫描全部公开上传目录；
- 构建拒绝 `public/uploads` 中的符号链接、特殊文件和普通非图片文件。

## 6. 实现方法

`MEDIA_BUDGET` 是 Node 侧的权威常量。检查器先用 `stat` 执行便宜的普通文件与体积判断，再调用 Sharp 元数据读取；这样超大伪造文件不会先进入解码器。AVIF 的扩展名不能直接与 `metadata.format` 字符串比较，因为 Sharp 报告底层容器为 `heif`，还需确认 AV1 compression，因此映射与判断明确记录该差异，输出时仍向作者显示 AVIF。

多页图片用 `pageHeight` 作为单帧高度、`pages` 作为帧数，避免把所有帧拼接后的总高度误当单帧尺寸。JPEG 等带方向元数据的单页图片优先使用 `autoOrient` 宽高。检查顺序保持稳定：类型、文件属性、体积、解码、格式、宽高、单帧像素、动图总像素，错误总带 `[media] <path>` 前缀。

Obsidian 发布器在任何写入前建立附件检查结果表。检查模式只格式化这份结果；正式模式沿用已通过的文件，然后才写正式 Markdown、删除收件箱草稿和移动附件。完整质量门仍负责最后兜底并保留既有回滚。Studio 的 JavaScript 配置无法浏览器导入 Node/TypeScript Sharp 模块，因此只导出同值体积常量，由测试强制与权威预算相等；真实格式和像素仍以构建门为准。

Windows 专项测试暴露 libvips 默认操作缓存会在 `metadata()` 完成后短暂保留输入句柄，导致立即删除/移动 WebP 报 `EBUSY`。媒体策略关闭此短命校验进程的 Sharp 缓存，并在 `finally` 销毁管线；随后测试和真实发布都能立即移动/清理附件。这里不能用延时重试掩盖，因为发布器承诺确定性地先检查后移动。

纯净 Git 检出还有另一条边界：Git 不保存空目录。在尚未提交第一张图片时，开发机可以保留空 `public/uploads`，Vercel 检出却没有该路径。扫描器先检查根上传目录；根目录不存在等价于零张图片，存在后则严格递归，子项读取错误不会被当成空仓库吞掉。

## 8. 经验与教训

- 扩展名白名单只验证名字，不验证内容；安全、可维护媒体必须以解码结果为准；
- AVIF 的用户格式名与底层解码器标识不同，格式契约要显式建模，不能假设字符串相等；
- 动图的总高度和单帧高度不是同一指标，预算必须同时约束单帧和总解码成本；
- 体积门应在解码前执行，降低损坏/恶意大文件的处理成本；
- UI 早期限制提升体验，但只有构建扫描才能覆盖 Studio、Obsidian 和普通 Git 三个入口；
- “检查后立即移动”在 Windows 上是一条真实平台不变量，测试必须包含句柄释放而不只是读取成功；
- 自动压缩会改变证据，不应偷偷塞进格式门；拒绝和可操作诊断是更清晰的第一阶段边界；
- 动态生成测试图片比长期维护二进制 fixture 更容易验证尺寸边界，也不会污染 Git 历史。
- 本地存在的空目录不是 Git 仓库结构；任何构建期目录契约都必须在纯净检出中验证“尚未创建”的合法状态。
