# 同一内容集合可以有两种时间顺序

关联：[[STATUS|当前项目状态]] · [[0129-atom-update-feed|Iteration 0129]] · [[0127-syllabus-order-vs-subscription-order|课程顺序与订阅顺序]] · [[0121-rss-extension-and-feed-time-semantics|RSS 修改语义]]

## 排序不是数据的固有属性

同一组文章并不存在唯一“正确顺序”。顺序回答的是一个具体任务：

- 读者想知道最近首次发布了什么：按 `publishedAt` 倒序；
- 读者想知道最近真正修改了什么：按 `updatedAt ?? publishedAt` 倒序；
- 读者想连续学习一个专题：按作者声明的 `series.order` 升序；
- 维护者想看发布与更新历史：把一条记录投影为多个事件再按事件日排序。

如果为了统一实现而只保留一个全局排序，至少会破坏其中一个任务。数据集合是事实，排序是消费语境。

## 不要篡改发布时间表达更新

最危险的捷径是：旧文章修改后直接把发布日期改成今天。它看起来能让 RSS 重新置顶，但同时改写了首次发布历史、档案分组、规范结构化数据和读者引用语境。

正确模型保留两个字段：

```text
publishedAt = 首次公开事实（稳定）
updatedAt   = 真实内容变化（可选、只前进）
```

不同协议再选择合适的投影：

```text
RSS  item pubDate       ← publishedAt
RSS  dcterms:modified   ← updatedAt（存在真实更新时）
Atom entry published    ← publishedAt
Atom entry updated      ← updatedAt ?? publishedAt
```

这样“更新提醒”和“历史真实性”不再互相冲突。

## 稳定决胜也是公开契约

只写“按更新时间倒序”还不够。同一天可能有多条记录，而内容日期只有日粒度；如果不显式决胜，文件系统遍历、数组输入或运行时 locale 差异会让 Feed 顺序抖动，正文摘要和缓存标签也随之变化。

Iteration 0129 的 Atom 顺序是：

1. `updatedAt ?? publishedAt` 倒序；
2. `publishedAt` 倒序；
3. 标题按 `zh-CN` 升序；
4. URL 按 `en` 升序。

生成器先复制输入再排序。这个规则既稳定，又能解释同日更新为什么以该顺序出现；测试必须打乱夹具输入，证明顺序来自契约而不是碰巧来自目录。

## 多种投影不等于重复事实源

RSS 与 Atom 可以同时存在，只要它们：

- 消费同一公开 `ContentRecord`；
- 复用相同规范 URL、标题、描述、正文和 tags；
- 只在被明确命名的时间语义上不同；
- 通过跨格式测试证明字段对齐；
- 不各自维护内容清单。

重复风险发生在订阅动作层，而不是数据层。本站在 `/subscribe` 同时展示 RSS 与 Atom，让读者主动选择；但 OPML 只导入 RSS，避免一次操作创建两个全站重叠频道。这说明“协议可用性”和“默认选择”应分开设计。

## Feed 自身还有第三种时间

entry 的 `updated` 描述内容；Feed 顶层 `updated` 描述整个序列化表示。即使所有文章日期不变，Atom 格式本身增加字段或修复序列化错误，也会改变表示。Feed 顶层时间与 HTTP Last-Modified 因此应取以下较新者：

```text
max(Atom 表示修订时间, 全部公开记录的最新内容日期)
```

它不能取当前构建时间或部署时间，否则完全相同的正文会在每次发布时伪装成新资源。表示修订必须显式、可审计、只在正文契约变化时推进。

## 可复用经验

“事实集合 + 语境投影”适用于更多场景：课程目录与更新流、创建日与最近编辑、按相关性与按时间的搜索、项目里程碑与活动事件。先给用户任务命名，再选择排序字段；如果两个任务都真实存在，就保留两个显式投影，而不是把一个顺序包装成万能答案。

每个投影还要回答四个问题：身份是否稳定、决胜是否确定、输入是否不变、默认入口是否会造成重复。只有这四项都能被测试和解释，多个视图才是能力扩展，而不是数据分叉。
