# 用独立事件账本分离首发、更新与复核

关联：[[STATUS|当前项目状态]] · [[0119-content-activity-ledger|Iteration 0119]] · [[0118-discovery-date-semantics|探索视图日期语义]]

## 三种时间回答三个问题

```text
publishedAt  内容何时首次公开？
updatedAt    内容事实何时真正变化？
reviewedAt   内容何时被复核？
```

它们不能因为都是日期就进入同一时间线。首发和更新是读者可感知的内容事件；复核可能没有改动正文，只是作者确认内容仍然有效。把 REVIEWED 放进变化流会制造不存在的新版本。

## 用投影而不是修改源记录

活动页不需要新的 frontmatter 数组。它从统一公开记录纯派生：

```text
每条记录 → 1 × PUBLISHED
updatedAt > publishedAt → 再加 1 × UPDATED
其他情况 → 不增加事件
```

源记录仍服务 archive、搜索、知识图、Feed 和内容清单。事件只包含模式、日期、类型、标题、摘要、URL 与稳定 id，避免 UI 获得不需要的作者字段。

## 确定性顺序

排序键依次是：

1. 事件日期倒序；
2. 同日 UPDATED 在 PUBLISHED 前；
3. `zh-CN` 标题；
4. `en` URL。

测试必须反转输入数组仍得到相同结果，并断言原数组未被修改。同日模式顺序需要产品明确决定，不能依赖 JavaScript 稳定排序碰巧保留的输入顺序。

## 三个视图保持不同职责

- archive：只按 `publishedAt` 回答首次形成；
- search/knowledge：显示当前版本日期，但保持原搜索/图谱顺序；
- activity：按事件日期展示首次发布和真实更新。

共享源事实不等于所有视图共享同一排序。分离 view-model 能让每个页面保持清晰承诺，同时避免复制内容数据。

## 验证与预算

纯函数夹具覆盖晚更新、同日更新、同日跨模式、标题/URL 决胜、空集合和输入不变。SSR 与生产 smoke 再验证事件数量、日期组、真实链接、零 REVIEWED、archive 入口与 Sitemap。新页面必须先部署到稳定生产域名，再冻结 raw/gzip 基线；本地输出不能为自己的增长背书。

## 可复用经验

当源实体有多个时间戳时，先为每个时间戳写出它回答的用户问题，再决定它属于排序键、展示字段还是事件。事件流是源实体的派生读模型，不必反向污染写作 schema。视觉上也应让模式可被形状和文字区分，不能只依赖颜色。
