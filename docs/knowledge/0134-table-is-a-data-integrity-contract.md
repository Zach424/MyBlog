# 表格首先是数据完整性契约，不是二维 CSS

关联：[[STATUS|当前项目状态]] · [[0134-constrained-technical-tables|Iteration 0134]] · [[0133-gallery-is-an-ordered-evidence-contract|画廊首先是有序证据契约]]

## `<table>` 只证明浏览器能排成网格

一个合法 HTML 表格不一定是一份可信技术数据。它可能没有标题、表头重复、数据行少一列、未知值留空、图片塞进单元格、移动端撑破页面，或者打印时只剩半张宽表。

完整边界应是：

```text
可迁移的标题 + GFM 表格
  → 列 / 行 / 单元格 / 内联内容预算
  → 表头唯一与每行列数严格相等
  → Studio 或 Obsidian 作者入口
  → 服务端语义 HAST
  → 桌面阅读 / 窄屏局部滚动 / 打印
  → 搜索纯文本与 Git/Vercel 交付
```

CSS 是最后一层投影，数据完整性必须在内容进入正式记录之前成立。

## GFM 的宽松行为不能直接当发布规则

GFM 允许数据行比表头短，也允许更多单元格；渲染器会补空或忽略超额值。这对手写草稿很宽容，对性能表和兼容矩阵却危险：数据可能静默移动、消失或失去列身份。

因此发布契约应检查 mdast 中每个 `tableRow` 的真实 `tableCell` 数量，要求它恰好等于表头列数。未知值不能留空，明确写“—”比让读者猜测“无数据、零、未测还是不适用”更诚实。

## 标题和唯一表头是最小身份

标题回答“这组数据在比较什么”，表头回答“每个值属于什么维度”。没有标题的表格在目录、屏幕阅读器、搜索摘录和脱离上下文的截图中都很脆弱；重复表头则让列引用产生歧义。

标题不是表格上方随意的一段文字。把它绑定到同一个受约束区块，才能让校验、公开标题、region 名称、Studio 表单和搜索使用同一事实。

## 预算要按数据规模，而不只按文件字节

只限制“最多 20 行”不够：20 行 × 2 列和 20 行 × 20 列的阅读、DOM 与编辑成本完全不同。表格至少需要五层预算：

- 列数；
- 数据行数；
- 单表数据单元格数；
- 单篇表格数；
- 单篇数据单元格总数。

当前 2–6 列、1–20 行、每表最多 120 个数据单元格、每篇最多 4 表/240 个数据单元格，使错误反馈和页面规模都保持可解释。

## 对齐是作者语义，不是字符串猜测

`42 ms`、`1.20%`、`v1.44.0` 都含数字，但它们不一定承担相同角色。渲染器根据正则自动右对齐会把展示规则藏进代码，也会在单位、范围或本地化格式出现时产生意外。

GFM 分隔行的冒号已经提供左、中、右对齐语义。作者或结构化 Studio 控件应显式选择，服务端只忠实保留。

## 首列冻结只保存上下文

宽表横向滚动时，第一列通常是环境、版本或方案名称。固定它能让读者在查看右侧指标时仍知道当前行是谁，这是阅读上下文，不是数据库主键，也不意味着该列可排序。

sticky 必须限制在表格内部：页面不能横向溢出，滚动 region 要有名称、可键盘聚焦并显示焦点；打印时要解除 sticky，让纸面回到普通表格流。

## 作者端结构化，不代表读者端交互化

Studio 用可增删、重排的列与行降低编辑错误，但最终仍序列化为普通 GFM。读者端不需要复刻编辑器，也不需要排序按钮、过滤状态、虚拟滚动或数据网格依赖。

这条分层很重要：作者体验可以接近文档工具，公开事实源仍然开放；读者获得快速、可搜索、可打印的静态证据。

## 可复用判断

1. 表格先定义标题、表头、行列一致和失败语义，再设计视觉；
2. 宽松 Markdown 解析不等于宽松发布契约；
3. 未知值应显式表达，不能用空单元格隐藏语义；
4. 规模预算要同时覆盖行、列、单表和单篇总量；
5. 对齐应由作者声明，不由渲染器猜测；
6. 首列冻结服务阅读上下文，不应扩张成排序或数据库语义；
7. 作者端可使用结构化表单，但必须输出可迁移的事实源；
8. 局部滚动要同时验证页面宽度、region 焦点和 sticky 几何；
9. 打印是独立投影，需要解除屏幕优化并重复表头；
10. 合成夹具证明布局能力，真实公开样本证明最终作者与生产体验。
