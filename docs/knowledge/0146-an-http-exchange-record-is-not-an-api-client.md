# HTTP 交换记录不是 API 客户端

## 结论

技术博客中的 HTTP 证据，价值在于把“为什么调用、向哪里调用、公开了哪些请求事实、观察到什么响应、如何验证”保存在同一个可审阅边界。只贴一段 JSON 会丢失方法、状态和上下文；复制完整调试会话又很容易把凭据、Cookie 和噪声一起发布。

## 静态记录与执行工具必须分界

Send、Replay、变量、鉴权、Cookie jar、重定向跟踪和代码生成一旦出现，组件就需要处理网络权限、凭据生命周期、CORS、失败重试、远程副作用和历史状态。个人博客没有必要承担这些责任。

可靠的第一版只保存作者已经脱敏、已经核对的文本投影。若读者需要复现，应由正文解释前置条件，并链接专用测试脚本或仓库；博客本身不重放请求。

## 脱敏是多层约束

只禁止 Authorization 不够。秘密可能出现在：

- URL 用户名、密码与查询参数；
- Cookie、Set-Cookie、API key 与自定义 token 头；
- JSON/form/text 正文；
- 验证说明或错误输出；
- Bearer/Basic、JWT、GitHub token、云访问键与私钥文本。

因此解析器必须同时检查名称和内容，并限制总长度。自动检测只能拦住已知模式，作者仍要在内容进入 Git 前人工脱敏。

## NONE 应该是显式语义

没有请求头、没有请求体、没有响应体，都是有效且重要的事实。用 `NONE` 明确表达，可以区分“协议上确实没有”与“作者忘记填写”。它也让 HEAD、204、304 等无正文规则能够跨字段验证。

## Content-Type 是正文的契约

正文围栏标成 json、xml 或 form 只是展示声明；只有与头字段中的 Content-Type 对齐，读者才知道这份证据自洽。反过来，NONE 不应要求 Content-Type，也不应偷偷保留一个空代码围栏。

## 搜索需要 payload，但不需要模板噪声

读者可能搜索端点路径、字段名、状态码、响应内容或验证结论，所以脱敏头值和正文应该进入纯文本索引。REQUEST HEADERS、RESPONSE BODY、VERIFICATION、围栏和 marker 只是结构，不应挤占命中片段。

## 可复用原则

一条可靠的 HTTP 交换记录在 CSS 丢失、JavaScript 关闭、复制进 Obsidian、通过 Git diff 审阅或只剩搜索纯文本时，仍能回答七个问题：为什么记录、请求方法是什么、目标在哪里、公开了哪些请求事实、观察到什么响应、哪些内容被刻意省略、作者如何验证。

打印时应把“验证区标题 + 验证列表”作为一个分页单元。只保护列表项会允许标题孤留上一页；对外层分组使用 `break-inside: avoid-page`，再把实际 PDF 渲染成图片检查，才能证明纸面证据没有被分页误导。
