# 在探索视图中分离显示日期与排序日期

关联：[[STATUS|当前项目状态]] · [[0118-discovery-update-dates|Iteration 0118]] · [[0117-published-versus-updated-dates|首发时间与维护时间]]

## 问题

统一内容记录同时包含 `publishedAt` 和可选 `updatedAt`，但搜索索引、知识图节点等派生对象经常只复制自己最初需要的字段。源数据正确并不能防止派生视图丢失语义。

当探索界面补显示更新时间时，又容易出现第二个错误：直接把排序也改成更新时间。这样会把“告诉读者当前版本何时形成”偷换成“重新定义发现顺序”。

## 最小派生契约

```text
ContentRecord
  ├─ publishedAt: string
  └─ updatedAt?: string

SearchDocument / KnowledgeGraphNode
  ├─ publishedAt: string     # 既有排序事实
  └─ updatedAt?: string      # 可见日期所需的最小新增事实
```

跨 Server/Client 边界只增加一个可选 ISO 字符串。不要传 Date、presenter 函数、完整作者记录或服务端读取能力。

## 用冲突夹具证明两件事

最有效的测试不是给普通记录补一个更新日，而是故意制造冲突：

```text
A: published 2026-07-01, updated 2026-09-01
B: published 2026-08-01, no update
```

期望同时成立：

1. A 的派生对象保留 `updatedAt: 2026-09-01`；
2. B 仍排在 A 前面，因为当前契约按 `publishedAt` 排序。

单个夹具由此同时防止字段再次丢失和排序被无意改写。

## 文案也属于排序契约

如果空搜索按首发日排列，却写“最新记录”，读者会自然理解为按最后更新时间排序。正确文案应完整闭合：

```text
按首发时间显示全部记录
行尾原因：首发顺序
可见日期：UPDATED / 2026-08-06
```

UPDATED 描述记录版本，首发顺序描述列表行为。两者可以同时成立。

## 同一语义，不同媒介

搜索列表适合纵向显示：

```text
PROJECT
UPDATED
2026-08-06
```

SVG 节点空间固定，适合紧凑单行：

```text
PROJECT / UPDATED / 2026-08-06
```

共享的是 presenter 结果，不是强制复用同一个 DOM 组件。移动端隐藏 SVG 时，关键日期要在保留的原生 HTML 路径中仍然存在。

## 验证层次

1. 纯函数用冲突夹具证明字段传播和首发排序；
2. SSR 证明搜索、SVG 节点和孤立记录使用真实更新日；
3. SSR 证明空搜索使用“首发时间/首发顺序”；
4. 390px 深色验证搜索层级、移动图谱降级和零横向溢出；
5. 1280px 深色验证 SVG 日期与计数、标题不重叠；
6. archive 反向断言继续隔离；
7. 本地与生产 HTML 预算证明客户端序列化增长受控。

## 可复用经验

显示字段、排序字段和筛选字段应分别命名。一个界面可以显示最近维护日，同时仍按首发日或相关性排序；只要文案和测试把这两层说清楚，就不需要为了“看起来统一”牺牲既有发现行为。

派生 view-model 应遵循最小充分原则：只复制消费者需要的事实，但每次新增消费者语义时都要回到投影边界审计。共享纯 presenter 能消除比较规则漂移，冲突夹具则负责防止行为漂移。
