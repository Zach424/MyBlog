# 时间线记录历史，不替代日历与任务系统

技术博客中的项目时间线，最有价值的不是“画一条竖线”，而是把已经发生的关键判断压缩成可审阅证据。日期、事件类型、标题和说明足够表达历史；负责人、截止时间、提醒、完成按钮和未来计划属于另一类产品。

## 先分清事实的时间方向

历史事件可以在发布时验证：日期是否真实、是否晚于当前内容日、顺序是否从早到晚。未来事项只能表达意图，还会随资源、优先级和外部依赖变化。如果把两者放进同一组件，读者很难判断某条是证据还是承诺，维护逻辑也会被迫加入状态更新、提醒和过期处理。

因此第一版时间线应明确拒绝未来日期。计划仍可以写在普通正文或独立任务系统中，等事件真正发生后再进入历史时间线。

## ISO 格式不是完整校验

正则只能证明 `2026-02-30` 长得像日期，不能证明它存在。可靠做法是按 UTC 零点解析，再把结果格式化回 `YYYY-MM-DD` 与原值比较。使用 ISO 日期还有一个好处：字符串比较就等价于日序比较，不需要引入时区或本地化解析。

同一天可以发生多个事件。若作者用列表顺序表达“先决定、再交付”，解析器应允许相同日期并保留顺序；只拒绝“日期 + 规范化标题”都相同的重复事件。

## 开放 Markdown 与结构化编辑可以共存

块引用和无序列表让普通阅读器也能看到日期、类型、标题和说明。Studio 可以把这些字段投影成日期选择器、类型下拉框和可拖动列表，但保存结果仍是相同 Markdown。这样编辑体验更友好，却不会把内容锁进 CMS 私有 JSON。

服务端契约仍然是最后边界。浏览器表单可以提前提示，但构建必须重复验证日期、类型、排序、预算和未来边界，防止直接 Git 编辑或旧客户端绕过规则。

## 视觉应该表达证据，不制造行为

Release Tape 的日期磁带、事件类型戳和纵向轨迹能帮助扫读，但语义必须保留在 DOM：原生有序列表表达顺序，`<time datetime>` 表达机器可读日期，标题和说明是普通文本。动画、滚动进度和“今天”游标不会增加历史证据，反而会引入客户端状态。

移动端要检查日期列和长说明是否同时成立；打印要允许长时间线跨页，但避免单条事件被切断。阅读端和作者预览是两个 CSS 发送边界，不能只验证其中一个。

## 验证环境也有“时间线”

本地端口可能仍运行上一次构建。HTTP 200 只证明某个服务可访问，不证明它包含当前代码。浏览器验收应核对监听进程、重新启动当前 production build，并从 DOM 中检查新能力的独有标记、计数和语义元素。否则旧构建也可能给出看似正常的截图，形成假绿。

## 可复用结论

一条可信的技术时间线是作者确认过的历史账本。它保存已发生事实、拒绝未来承诺、使用开放语法、保留机器日期语义，并在构建端失败关闭。需要提醒、协作或计划时，应使用真正的日历或项目管理系统，而不是把文档组件扩成半成品应用。
