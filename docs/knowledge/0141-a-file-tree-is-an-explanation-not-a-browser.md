# 文件树是结构解释，不是在线浏览器

技术文档里的文件树解决的是“这些目录和文件为什么存在”，而不是“我现在能否像 IDE 一样操作仓库”。两者看起来相似，数据和维护责任却完全不同。

## 最小可迁移事实

一棵可发布文件树只需要四类事实：可见标题、路径层级、文件/文件夹类型、节点职责。块引用提供区块边界，嵌套无序列表提供层级，行内代码提供路径信号，文件夹末尾 `/` 提供类型。普通 Markdown 阅读器即使不认识专用 marker，仍能读懂结构。

完整路径不应由作者在每层重复保存。解析器携带祖先路径段派生完整路径，再用完整路径做 NFKC 和大小写规范化判重。这样既允许 `app/page.tsx` 与 `studio/page.tsx` 并存，也能拒绝同一位置的全角或大小写变体。

## 为什么不做折叠与远程读取

折叠、选中、在线文件内容和远程仓库状态都会把静态说明变成浏览器应用：需要客户端状态、网络失败态、权限、缓存、分支/提交身份和更复杂的可访问性。更严重的是，读者可能误把实时仓库视图当作作者对架构边界的解释。

静态文件树把责任放回内容复核：作者选择对论述必要的仓库切片，并用说明解释它。源文、搜索、复制、无 JavaScript 阅读和打印都得到相同结构。仓库变化时，更新正文与 `reviewedAt`，而不是让远程 API 在每次访问时悄悄改变文章证据。

## 编辑投影可以不同，存储事实必须相同

递归列表适合阅读和版本 diff，却不一定适合表单编辑。Studio 可以让作者按顺序填写完整相对路径，并检查每个子路径之前已有父目录；保存时再重建嵌套列表。只要解析已有 Markdown 能还原同一顺序和路径，这仍是一个事实源，不是两套模型。

## 验证重点

- 文件不能拥有子节点，文件夹才是层级容器；
- 节点数、深度和单篇总量必须受限，避免把整个仓库倾倒进正文；
- 路径段拒绝分隔符、控制字符、`.` 与 `..`；
- 说明只接受可安全内联渲染的内容；
- 320 px 要同时验证缩进、长路径和长说明，而不只是页面总宽；
- 打印应保留全部节点并允许长树自然跨页；
- 合成渲染只能证明格式成立，结构事实仍需作者复核。

## 可复用结论

好的文档文件树是经过选择的“仓库切片”。它解释边界、入口和职责；它不承诺实时、不代理 Git、不保存界面状态。作者工具可以更方便，但最终产物应仍是一段开放、可审阅、可搜索和可版本控制的 Markdown。
