# 富 Markdown 应该是语法树契约

关联：[[STATUS|当前项目状态]] · [[0130-obsidian-markdown-callouts|Iteration 0130]] · [[0129-one-content-set-can-have-two-time-orders|同一内容集合可以有两种时间顺序]]

## 不要把富内容当成字符串装饰

Callout 看起来只是把 `> [!warning]` 换成一个有颜色的块，但全局字符串替换会立刻遇到四类问题：代码示例被误改、嵌套边界不清、正文 Markdown 丢失、生成 HTML 难以保证安全。真正稳定的边界是语法树：Markdown parser 先确认 blockquote、段落、代码围栏和内联节点，再由转换器只改它拥有的结构。

```text
Markdown source
  → mdast（代码与引用已经分型）
  → HAST（HTML 语义已经显式）
  → 受限 Callout 转换
  → React / Studio HTML / 搜索投影
```

正则仍然有用，但只能在已经缩小的节点内解析首行标记。它不应该负责发现整篇文档中的嵌套、代码和 HTML 边界。

## 共享语义，不复制 renderer

读者页面和 Studio 的目标相同：作者保存后看到什么，生产页面就应渲染什么。因此二者共享 `MARKDOWN_REHYPE_PLUGINS`，Callout 与 KaTeX 只实现一次。Studio 浏览器端的快速扫描不是 renderer，它只回答“这段正文是否可能需要向服务器请求增强预览”；即使扫描偶尔保守，多发一次请求也不能改变最终语义。

搜索则需要不同输出，但仍应消费同一作者协议。它不需要 HTML，只需移除 `[!warning]` 并保留“发布前检查 + 正文”。这说明共享契约不等于所有消费者调用同一个函数，而是每个消费者都从同一 AST 身份与可见语义派生，不维护另一套字符串解释。

## 原生平台能力是最小交互层

折叠 Callout 用 `<details><summary>`，没有客户端状态机：

- 键盘和鼠标可直接使用；
- JavaScript 失败时仍可读；
- 默认 open 是 HTML 属性，不需要水合；
- 深浅色与打印只需要 CSS；
- 测试可以检查真实 DOM 状态，而不是模拟框架内部事件。

但屏幕状态不能直接成为打印状态。默认收起的 `<details>` 在打印时可能丢失正文，因此 print CSS 必须明确显示 body 并隐藏加减号。渐进增强的完整含义是：交互存在时更方便，不存在或媒介改变时信息仍完整。

## 兼容性首先体现在“不改变什么”

新增语法最重要的测试往往不是“新语法成功”，而是：普通 blockquote 不变、代码围栏示例不变、非法标记不变。旧内容已经依赖这些行为，误转换的成本高于拒绝一个新写法。

未知类型采用受限降级：只接受英文开头、英文数字连字符、最长 32 位；结构按 note 输出，但保留来源 type 文本。这样作者从其他 Obsidian Vault 复制内容时不会丢正文，又不会借自定义标识符开放任意 class、CSS 或脚本入口。

## 可复用检查表

为 Markdown 增加图表、视频或其他富内容前，先回答：

1. parser 在哪个 AST 阶段能准确识别它？
2. fenced code、普通引用和旧内容如何保持不变？
3. 生产阅读与作者预览如何共享实现？
4. 搜索、源 Markdown、Feed 和打印保留什么语义？
5. 无 JavaScript、窄屏、深色和辅助技术下如何降级？
6. 输入、节点、输出字节和递归深度如何限制？
7. 失败时是拒绝发布、保留源码，还是安全降级？
8. 生产 smoke 如何在不改公开文章的情况下证明能力？

只有这些边界都能在测试与文档中说明，富 Markdown 才是可维护的内容协议，而不是一段容易漂移的视觉魔法。
