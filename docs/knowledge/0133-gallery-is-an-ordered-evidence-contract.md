# 画廊首先是有序证据契约，不是图片网格

关联：[[STATUS|当前项目状态]] · [[0133-constrained-multi-image-gallery|Iteration 0133]] · [[0132-video-is-a-publishing-contract|视频首先是发布契约]]

## `display: grid` 只解决最后一层

把若干 `<img>` 放进两列网格很容易，但它没有回答：图片是否属于同一内容、顺序是否重要、每张图说明什么、看不到图时还剩什么、作者如何重排、附件如何归档、移动和打印如何降级、错误素材如何阻止发布。

完整边界应是：

```text
可迁移 Markdown 声明
  → 组标题 / alt / caption / 数量 / 顺序契约
  → Studio 或 Obsidian 作者入口
  → 当前 slug 媒体归档与真实图片门
  → 服务端语义 HAST
  → 桌面接触表 / 窄屏单列 / 打印
  → 搜索纯文本与 Git/Vercel 交付
```

因此画廊是内容模型，网格只是其中一个读者投影。

## 顺序本身就是证据

项目步骤、修复前后和多状态对比都依赖顺序。作者可以重排，是因为作者正在编辑证据；读者端不应按文件名、图片尺寸或加载完成时间重新排序，也不需要一个会隐藏后续帧的轮播。

有序列表能同时给 HTML、屏幕阅读器、打印和纯文本处理提供稳定身份。`FRAME 01` 不是装饰计数，而是把视觉顺序显式化，让引用和复核更容易。

## 三种文字不能互相代替

- 组标题：说明这一组图片共同证明什么；
- 短标题：标识某一帧的角色或阶段；
- alt：在图像不可见时传递该帧的关键状态和结果。

用文件名自动补 alt、用短标题复制 alt、或用“截图一/截图二”填空，都会让画廊在搜索、无障碍和文件失效时失去内容价值。字段全部必填比智能猜测更诚实。

## 静态接触表优先于轮播

轮播一次只暴露一帧，会降低比较效率，也为键盘、触摸、打印、无 JavaScript 和状态持久化制造额外契约。技术博客的主要任务是理解关系，而不是延长停留时间。

静态两列接触表让读者同时看到上下文；窄屏按原顺序变为单列；打印保留所有帧。只有在图片数量远超当前 2–6 张边界、并且有明确放大任务时，灯箱或分页才值得重新评估。

## 保留完整图像比填满舞台重要

技术截图、图表和终端输出的边缘常包含关键证据。`object-fit: cover` 会为了视觉填满而裁掉内容，适合装饰照片，不适合证据图。4:3 舞台配合 `object-fit: contain` 接受留白，换取完整像素语义。

## 可迁移语法降低工具锁定

```markdown
> [!gallery] 发布流程证据
> - ![编辑器里的结构化画廊表单](/uploads/release-flow/editor.webp "编辑")
> - ![生产文章中的双栏证据组](/uploads/release-flow/published.webp "上线")
```

Obsidian 把它识别为 Callout，普通 Markdown 工具仍能看到一组图片列表，站点构建器再把精确结构提升为画廊。作者入口可以不同，事实源仍只有一份。

## 数量限制需要三个维度

只限制“每组最多六张”不够：作者可以创建大量组绕过页面预算。因此应同时限制单组图片数、单篇组数和单篇画廊总图片数。当前 2–6 张、最多 3 组、合计最多 12 张，让作者得到清楚反馈，也让构建、页面体积和移动阅读保持可解释。

## 可复用判断

1. 富媒体组件先定义内容身份、顺序和失败语义，再设计布局；
2. 作者工具可以提供结构化表单，但必须序列化为开放、可读的事实源；
3. 组级文字、项级标题和替代文本是三类不同证据；
4. 技术证据图优先完整显示，不为“铺满”裁切关键边缘；
5. 轮播、灯箱和手势不是默认升级，它们需要独立的读者任务与无障碍契约；
6. 单项上限之外，还要约束组数和全篇总量；
7. 新媒体组合应复用已有归档、校验、回滚和 Git 交付链；
8. 合成预览证明能力，真实公开内容证明最终传输，两者不能互相冒充。
