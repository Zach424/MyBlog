# 音频文字稿是正文，不是播放器附件

关联：[[STATUS|当前项目状态]] · [[0136-constrained-local-audio-notes|Iteration 0136]] · [[0135-task-state-is-published-evidence|任务状态是发布证据]]

## 播放能力不是知识可用性的前提

浏览器可能无法解码、网络可能暂时不可用、读者可能处于静音环境，也可能无法听见录音。如果知识只存在于 MP3 内，博客的搜索、引用、打印和长期迁移都会被文件播放能力绑架。

当前契约把标题、简述和完整文字稿直接写进 Markdown：

```text
本地 MP3
  + 标题 / 简述
  + 等价完整文字稿
  → 同一受约束 Markdown 块
  → 原生播放器 / 搜索 / 屏幕阅读 / 打印 / 公开源文
```

文字稿不是“可选辅助材料”，而是音频内容的正文投影。

## 音频是复合发布契约

只检查 `.mp3` 扩展名不够。可信发布至少需要四层：

1. 路径层：仓库内、当前 slug 所有、无查询参数和外链；
2. 文件层：真实 MPEG Layer III、体积/时长/码率/采样率/声道受限；
3. 语义层：标题、简述、文字稿必填且有长度预算；
4. 展示层：原生控件不自动播放，文字稿可直接读取，打印保留来源。

任何一层缺失，都会把错误推迟到读者端或让内容脱离 Git 审查。

## 浏览器预检和构建门职责不同

浏览器可以快速检查文件签名、体积、可解码时长和 SHA-256，同名冲突也能在文件进入 Git 草稿前提示。但它不能稳定证明所有 MP3 编码细节。

构建门使用 `music-metadata` 解析真实容器、codec、码率、采样率和声道，并再次验证体积与时长。浏览器负责及时反馈，构建负责发布权威；前者通过不能覆盖后者。

## 原生控件优于复制播放状态

第一版只需要 `controls` 和 `preload="metadata"`。浏览器已经提供键盘操作、时长、进度、音量和平台辅助能力。自行实现波形、播放按钮、进度和音量会引入第二套状态、更多客户端代码和更大的无障碍验证面。

Evidence Rail 可以提供视觉身份，但不能替代原生 `<audio>`。装饰刻度属于 CSS，播放事实属于浏览器。

## 搜索索引文字，而不是文件名

文件名常常只是 `release-retro.mp3`，几乎没有检索价值。搜索应保留标题、简述和完整文字稿，同时删除 `[!audio]`、下载文案和 `/uploads` 路径噪声。

这也让公开 Markdown、Atom/Feed 的纯文本投影和后续知识关系能够消费真实内容，而不是媒体实现细节。

## 可复用判断

1. 单媒体 URL 不是完整的音频发布模型；
2. 等价文字稿应进入正文和版本历史，而不是远程播放器元数据；
3. 路径、文件、语义和展示四层都要有失败关闭的契约；
4. 浏览器预检追求及时，构建门负责权威，两者不能互相冒充；
5. 原生播放器负责播放状态，设计系统只负责证据结构和外观；
6. 搜索应索引人类含义，不索引作者 marker、下载文案或文件路径；
7. 非视觉媒体复用通用附件事务时，要明确占位尺寸不是真实媒体属性；
8. 合成预览可以证明 HTML/CSS/语义，不能证明真实文件、Range 或 CDN；
9. 自动转写只有在隐私、质量、成本和校对责任明确后才应加入；
10. 当音频需要章节、播客分发或统计时，应先建立独立产品契约，不把第一版无限扩张。
