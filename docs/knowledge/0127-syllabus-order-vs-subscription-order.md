# 课程目录顺序与订阅变化顺序应分离

关联：[[STATUS|当前项目状态]] · [[0127-series-rss-order-semantics|Iteration 0127]] · [[0126-route-specific-cache-boundaries|协议子路由缓存边界]]

## 数据相同，不等于任务相同

专题页面回答“我应该从哪里开始学”，RSS 回答“最近有什么新内容”。两者消费相同的公开专题记录，却服务不同时间视角：页面需要作者章节序，Feed 需要变化优先。

```text
series.order 1, 2, 3   → syllabus → 连续学习
publishedAt 3, 2, 1   → inbox    → 新内容提醒
```

如果 Feed 复制章节顺序，后来增加的章节可能沉到阅读器底部；如果页面复制时间倒序，新读者会先看到结论再看到前置约束。所谓“统一排序”反而会同时损害两个任务。

## 共享事实，不共享所有投影

正确复用边界是公开集合、内容身份和序列化规则，而不是最终排列：

- `getSeriesBySlug()` 决定成员资格；
- `series.order` 决定 HTML 教学目录；
- RSS serializer 的 `publishedAt` 倒序决定订阅流；
- 两者继续共享标题、URL、GUID、日期、标签和可见性事实。

这避免第二套内容库，也不需要新增 `feedOrder` 字段。只有未来出现明确的手动通知置顶需求时，才应把它作为新的公开产品语义评估。

## 测试要证明差异是有意的

只断言 Feed 有两项并不能防止排序漂移。契约应同时证明：

1. 专题页面路径严格为第 1→2 章；
2. Feed GUID 严格为第 2→1 章；
3. Feed 集合等于页面章节集合，没有漏项或越界项；
4. serializer 不修改调用方的章节数组；
5. 生产 smoke 复核相同差异，而不只在纯函数夹具中成立。

将两个相反顺序放进同一测试语境，能阻止维护者误以为它们需要“修正为一致”。

## 投影边界仍需完整协议保护

排序语义正确还不够。专题 RSS 是独立公开资源，必须拥有自己的 channel home/self、正文摘要、文件名、ETag、Last-Modified、条件 GET/HEAD 和未知资源 404。父级 `/series/:path*` HTML 缓存不能覆盖它，否则成功 Feed 或未知 Feed 的缓存都会漂移。

新资源不进入 Sitemap，但专题页面的可见链接、head alternate 与响应 Link 足以让人和阅读器发现它。Feed item GUID 保持规范文章 URL，因为专题只是投影语境，不是新内容身份。

## 可复用经验

当同一集合要出现在列表、搜索、时间线、课程目录和订阅源中时，先写下每个界面回答的问题，再决定排序。共享数据模型应保证成员资格和身份一致；投影层应允许为用户任务选择不同顺序。测试不仅要锁定各自结果，还要明确证明差异是设计，而不是偶然。
