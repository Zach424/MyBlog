# 决策记录是取舍台账，不是结果公告

## 结论

技术决策记录最重要的内容不是工具名，而是决定发生时的约束、未选择方案和已知影响。只写“采用 X”会留下结果，却删掉未来复盘真正需要的推理证据。

## 一个可靠的最小模型

一个可迁移的个人技术决策记录至少应保存：

1. Context：当时的问题、约束和目标；
2. Decision：明确、可引用的最终选择；
3. Rationale：为什么这个选择最符合当时约束；
4. Alternatives：真实考虑过但没有选择的方案及原因；
5. Consequences：正面、负面和中性影响；
6. Status / Date：决定当前语义和作出时间。

其中 Alternatives 与 Consequences 不是附录。它们共同阻止两种历史失真：把当时的选择误解为唯一可能，以及只保留成功结果、忘记已经接受的代价。

## 为什么需要固定结构

个人博客同时有多个作者入口和多个消费方式：Obsidian、网页 Studio、Git diff、搜索、普通 Markdown 阅读器、HTML 页面和打印。固定区段顺序能让这些边界共享同一份源事实。若允许作者任意命名或混排段落，每个入口都必须猜测语义，最终会产生多个不一致的解析器。

固定结构不等于封闭格式。块引用、粗体、行内代码和列表仍是开放 Markdown；离开本站后，即使自定义视觉消失，文字层级仍然可读。

## 状态不是审批系统

ACCEPTED、SUPERSEDED、DEPRECATED、REJECTED 描述的是已发布决定的状态，而不是待办按钮。第一版不应顺势加入投票、评论、审批和读者编辑，因为这些能力会引入身份、权限、通知、冲突和数据库，而它们并不提高一篇个人技术记录的可解释性。

## 搜索应保留什么

搜索应保留标题、日期、背景、决定、理由、方案与影响说明；应删除 marker、区段名、状态和 POSITIVE/NEGATIVE/NEUTRAL 等机械 token。读者通常搜索的是“为什么没用 Cloudflare”或“Vercel 平台耦合”，不是 `CONSEQUENCES` 这个字段名。

## 实现时容易忽略的边界

- ISO 格式合法不代表日期真实，需要日历往返验证；
- 方案名称要在 NFKC 后判重，避免全角字符制造伪唯一；
- tight Markdown list 的 HAST 可能没有 `<p>`，展示转换不能假定所有列表相同；
- 未来日期门要同时存在于编辑预检和正式构建；
- 打印应允许整个记录跨页，但不能切断单条取舍或影响；
- Studio 表单可以改善输入，但保存格式仍应是可移植 Markdown；
- 状态变化只能表达当前语义，若未来需要显式 superseded-by 关系，应建立新契约而不是从标题猜测。

## 可复用原则

先冻结事实结构，再设计视觉；先保存作者已确认的判断，再考虑自动化。一个好的决策组件应该在 JavaScript 关闭、CSS 丢失、搜索索引和 Git diff 中仍然讲清同一个故事。
