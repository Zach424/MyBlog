# 代码变更记录是一份审阅信封，不是一段彩色代码

## 结论

技术博客中的代码变更证据，核心不是把 `+` 染成绿色、把 `-` 染成红色，而是把目的、文件范围、实际修改、验证结果和已知风险装进同一个可审阅边界。缺少其中任意一项，diff 都容易退化成无法复用的视觉片段。

## 两种模式回答不同问题

Unified diff 适合回答“这次跨哪些文件改了什么”。它保留文件头、hunk 和增删行，是 Git、邮件和代码托管界面共同理解的文本证据。Before/after 适合回答“一个小片段从什么变成什么”，它对教学更直观，却不应冒充完整补丁。

两种模式应该在元数据中显式区分，并使用不同的固定结构。若让解析器根据内容猜测模式，缺失的文件头、错误的语言或不完整 patch 很容易被误当作合法展示。

## 文件清单必须是约束，不是目录装饰

FILES 最有价值的作用是给读者一个审阅索引，同时给系统一个可验证声明：

- 文件数量与 `diff --git` 文件段数量一致；
- 清单顺序与 diff 顺序一致；
- modified/added/deleted/renamed 与文件段元数据一致；
- rename 同时保存旧路径和新路径；
- 目标路径在规范化后不能重复。

这样，标题和目的无法用一个文件清单包装另一份无关 patch。

## 静态博客不要成为补丁执行器

一旦组件读取实时 Git、提供 Apply 或写回仓库，它就跨入了凭据、权限、分支状态、冲突处理和回滚边界。个人博客真正需要的是“已经复核的最小证据投影”，而不是另一个代码托管客户端。

因此第一版应明确关闭：

- 实时仓库读取与 commit 查询；
- patch 执行、文件编辑和自动提交；
- 自动生成目的、验证或风险；
- 行级评论、审批状态和读者持久化；
- 对 patch 真实性或可应用性的过度承诺。

## 代码预算也是内容设计

过长 diff 会吞噬文章主线，也会放大构建、高亮、移动端和打印成本。每块行数、字符数、单行长度与每篇总量都应有限；跨越预算时，作者应链接仓库提交，并在正文只保留最关键的审阅切片。

敏感内容检查必须先于高亮。私钥头、常见 GitHub token 与 AWS access key ID 应直接阻止发布；更广泛的秘密扫描仍由独立安全工具负责，博客解析器不应声称完整 DLP。

## 搜索应保留语义，删除 patch 噪声

读者会搜索文件名、函数名、旧实现、新实现、测试结果或风险，不会搜索 `diff --git`、`@@ -1 +1 @@`、PURPOSE 或 VERIFICATION。搜索投影应保留自然语言和有效代码，删除结构 token、文件头与 hunk 元数据。

## 可复用原则

一条可靠的代码变更记录在 CSS 丢失、JavaScript 关闭、复制进 Obsidian、通过 Git diff 审阅或只剩纯文本索引时，仍能回答五个问题：为什么改、改了哪里、具体怎么改、如何证明、还怕什么。
