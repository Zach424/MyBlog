# 定义是上下文知识，不是远程词典服务

关联：[[STATUS|当前项目状态]] · [[0139-constrained-glossary-definitions|Iteration 0139]]

## 术语表回答“本文怎样使用这个词”

技术文章里的定义通常带有项目和版本语境。例如 Server Component 的简短定义，可以帮助读者理解当前 Next.js 文章，却不等于一部跨框架、跨版本、自动更新的权威词典。

因此第一版只保存作者确认的四种事实：术语、定义、可选别名、可选上下文。它们和正文一起版本控制、复核和发布，不从远程服务自动改写。

## 名称唯一性需要覆盖别名

只检查术语名不重复仍然会留下歧义：一个条目的术语可能恰好是另一个条目的别名。正确的不变量是把术语与全部别名放进同一个规范化命名空间：

```text
normalize = NFKC + zh-CN lowercase
names = every term + every alias
要求：names 全局唯一（限同一个 glossary）
```

这不会推断语义同义词，只防止作者已经显式声明的名称发生冲突。

## 语义 HTML 和视觉布局各司其职

定义关系应该由 `<dl>/<dt>/<dd>` 表达；左右双栏、窄屏堆叠和上下文轨道由 CSS 表达。若只使用普通 `div` 做成两列，视觉上像术语表，辅助技术和内容提取器却看不到 term/description 关系。

现代 `<dl>` 可以使用 `div` 把对应的一个或多个 `<dt>` 和 `<dd>` 分组。这适合让每个术语及其解释成为同一个布局与打印条目，同时不破坏定义列表语义。

## 搜索应删除标签，不删除别名

`[!glossary]`、`别名：`、`上下文：` 是作者协议；RSC、Hydration 和上下文正文是读者会搜索的知识。搜索投影必须精准删除结构标签，保留人类意义。

另一个容易忽略的边界是：CSS `gap` 只改变视觉距离，不会自动在复制文本或无障碍名称中插入空格。相邻 alias chip 需要真实文本分隔，不能只依赖布局。

## 开放语法应先于编辑器表单

Studio 的嵌套列表能让作者增删和拖动术语，但最终仍序列化为普通块引用、无序列表和段落。Obsidian 模板生成同一格式。这样 GitHub、文本编辑器和未来迁移工具都能读取，不会把知识锁进 CMS 私有 JSON。

## 可复用判断

1. 先明确术语定义的适用语境，不把局部说明冒充全球词典；
2. 术语与别名应共享规范化唯一命名空间；
3. 定义关系用 `<dl>/<dt>/<dd>`，布局用 CSS；
4. 搜索删除协议标签，保留别名和上下文；
5. CSS 视觉间隔不能替代可访问文本分隔；
6. CMS 组件应生成开放格式，不成为第二事实源；
7. 专用 marker 的错误结构应失败关闭；
8. 列表延续段落的缩进需要真实解析器测试；
9. 合成生产预览能证明渲染契约，不证明定义内容本身正确；
10. 需要跨文档合并、自动翻译或协同审校时，应另建知识服务契约，而不是扩张静态内容块。
