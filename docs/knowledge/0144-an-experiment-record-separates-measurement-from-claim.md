# 实验记录要把测量与主张分开

## 结论

一条可信的技术实验记录不是“我试过，结果不错”，而是一条从假设、条件、方法和样本走向测量，再从测量收敛到有限结论的证据链。结论必须比测量更克制，局限必须与结论同样显眼。

## 最小证据模型

一个可迁移的个人技术实验至少应保存：

1. Hypothesis：运行前可被支持或反驳的明确主张；
2. Environment：硬件、系统、依赖、版本或数据条件；
3. Method：别人能理解并尽量复现的操作；
4. Sample：运行次数、数据范围或观察窗口；
5. Measurements：指标名、原始读数及其语境；
6. Conclusion：这组测量实际能支持的判断；
7. Limitations：不能从这组证据推出什么；
8. Status / Date：本次运行的结果关系和发生时间。

其中 Sample 和 Limitations 不能隐藏在散文里。没有样本边界，`187.1 s` 很容易从“一次本机运行”被误读成“稳定性能”；没有局限，SUPPORTED 很容易被误读成普遍规律。

## 状态只描述证据关系

SUPPORTED 表示本次测量支持假设，REFUTED 表示本次测量反驳假设，INCONCLUSIVE 表示证据不足，FAILED 表示没有完成有效测量。它们都不是成功率、统计显著性或最终真理。

失败与证据不足也应可发布。它们能记录已经尝试的环境和方法，减少后来重复相同错误。若只允许“成功实验”，博客最终会成为结果展板，而不是学习档案。

## 为什么不直接做实验平台

个人博客的主要任务是发布已经确认的知识，而不是承担远程执行、指标采集、运行排队、访问控制、原始数据存储和统计分析。这些能力会引入新的安全、成本、隐私和运维边界，却不会自动让作者的结论更严谨。

更合适的分工是：实验工具负责运行和原始产物，博客负责保存作者已经复核的最小证据投影。开放 Markdown 让这份投影能被 Git、Obsidian、Studio、普通阅读器、搜索和打印共同消费。

## 视觉不能制造不存在的精度

实验内容很容易诱发仪表盘、折线图、百分比和绿色成功徽章。但单个或少量样本通常没有足够信息支撑趋势与显著性。可靠的第一版应该突出指标名、原始值、说明、结论与局限，不从静态文本自动推导图表或排名。

## 实现边界

- ISO 字符串必须做真实日历往返验证；
- 构建和编辑预检都要拒绝未来运行日期；
- 测量名和局限名应在 NFKC 后判重；
- 测量值应使用独立的行内代码边界，避免与说明混淆；
- 搜索保留条件、方法、指标、值、结论和局限，删除区段名与状态噪声；
- tight list 的 HAST 可能省略 `<p>`，展示转换要兼容两种形态；
- 打印可以跨页，但不应切断单条测量或局限；
- Studio 表单改善输入，服务端契约仍应是最终权威。

## 可复用原则

先问“这次到底测到了什么”，再问“可以写下什么结论”。一个可靠的实验记录在 CSS 丢失、JavaScript 关闭、导出到 Git diff 或只剩纯文本搜索时，仍能让读者看清测量条件、证据和结论边界。
