# 顺序不是状态，流程也不是任务系统

关联：[[STATUS|当前项目状态]] · [[0138-constrained-procedure-steps|Iteration 0138]] · [[0135-task-state-is-not-task-management|任务状态不是任务管理]]

## 两种列表回答不同问题

步骤流程回答“应该先做什么、再做什么”；任务账本回答“哪些工作已经完成”。即使两者都能写成列表，它们的核心不变量并不相同：

```text
步骤流程：顺序改变 → 含义改变
任务账本：状态改变 → 当前快照改变
```

流程因此使用原生有序列表和固定编号，不使用 checkbox；任务账本可以展示完成状态，却不自动声称有严格执行先后。

## 验证条件是内容证据，不是应用状态

“命令以退出码 0 完成”描述读者怎样确认一步做对了。它不是系统替读者保存的执行结果，也不需要数据库。把验证条件投影为静态 CHECK 轨道，可以突出判断标准，同时保持 Markdown、打印和搜索都完整可用。

## 开放语法应先于编辑器表单

Studio 的嵌套表单可以让作者增删和拖动步骤，但最终必须序列化为普通块引用和有序列表。这样 Obsidian、GitHub、任意文本编辑器和未来迁移工具都能理解内容，不会把知识锁进 CMS 私有 JSON。

## 特殊 marker 必须失败关闭

如果作者写了 `[!steps]` 却遗漏标题、从 3 开始编号、嵌套列表或加入图片，静默退化为普通 Callout 会掩盖发布错误。候选一旦表明作者意图，就应该由专用契约给出行号诊断。

一个容易忽视的边界是：部分 Markdown 解析器会把错误的 `3.` 吞进前一段文字，而不是生成起始值为 3 的 list 节点。因此不能只检查 AST 的 `list.start`；还要对候选 marker 保留的原始文本做窄范围补充验证。

## 搜索和渲染服务不同任务

阅读端需要编号、轨道和 CHECK 标签来展示结构；搜索端只需要流程标题、步骤名、说明和验证正文。搜索若保留 `[!steps]` 与“验证：”会增加机器语法噪声，若删除验证正文又会丢掉读者真正会查找的结果证据。

## 可复用判断

1. 先判断内容结构表达的是顺序、状态、集合还是层级，再选择语义 HTML；
2. 顺序改变会改变含义时使用 `<ol>`，不要只靠视觉编号；
3. 验证标准可以是静态内容，不等于需要执行引擎；
4. CMS 组件应生成开放格式，不应成为第二事实源；
5. 特殊 marker 的错误结构必须失败关闭；
6. AST 规范化可能隐藏作者原始错误，必要时在候选文本上补窄范围校验；
7. 专用转换器必须在通用 Callout 之前消费自己的 marker；
8. 搜索投影保留人类意义，删除编辑器标记；
9. 浏览器同源由 scheme、host 和 port 共同决定，`localhost` 与 `127.0.0.1` 不可混用；
10. 需要分支、循环、负责人、期限或自动执行时，应建立真正的工作流系统，而不是无限扩张静态教程块。
