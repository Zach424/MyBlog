# 可选时间元数据也必须可证明

关联：[[STATUS|当前项目状态]] · [[0128-opml-subscription-bundle|Iteration 0128]] · [[0123-reuse-conditional-response-boundary|复用条件响应边界]]

## 能填写，不等于应该填写

[OPML 2.0 specification](https://opml.org/spec2.opml) 允许 head 包含 `dateCreated` 和 `dateModified`，但它们不是必填项。看到可选字段时，常见冲动是用构建时间、部署时间、当前时间或某个源码文件 mtime 填满它们；这样文档看似更丰富，实际上把流水线事件伪装成资源事实。

对聚合订阅文件而言，“修改时间”至少可能指：

- 任一文章最后修改；
- 任一标签/专题集合最后变化；
- OPML 序列化格式最后修订；
- 本次构建或部署完成；
- 边缘节点本次生成响应。

这些时间并不等价。只有前两项和格式修订共同覆盖后，才可能表示“这个 OPML 表示何时最后改变”。当前仓库没有一个精确、完整且可审计的时间值，因此最诚实的输出是省略日期。

## 内容摘要比伪造时间更可靠

确定性生成的资源可以直接对最终 UTF-8 字节计算 SHA-256：

```text
public subscription indexes
          │
          ▼
deterministic OPML bytes
          │
          └─ SHA-256 ETag → If-None-Match → 304
```

摘要回答的是“字节是否相同”，不需要猜测“变化发生在哪一秒”。只要生成器顺序稳定、所有输入来自同一公开索引，同样的集合与 origin 就得到同样的正文和 ETag；任一频道新增、删除、重命名或域名变化都会自然换摘要。

这比用 `new Date()` 生成 Last-Modified 更适合缓存：后者会让每次构建看起来都修改资源，即使字节完全相同；既降低缓存命中，也制造错误的历史信号。

## 日期条件请求有更高的证明责任

Last-Modified 不只是说明文字，它会参与 `If-Modified-Since` 判断。如果时间早于真实变更，服务器可能错误返回 304，让客户端继续使用陈旧文档；如果时间每次构建都变化，则客户端无法从未变正文中获益。

因此日期验证器必须同时满足：

1. 覆盖表示的全部变化来源；
2. 不晚于响应时间；
3. 粒度和时区语义明确；
4. 可以从仓库事实重复计算；
5. 与正文格式修订分开管理；
6. 进入 GET、HEAD、304 和生产边缘测试。

缺少任一条件时，只有 ETag 的实现通常更正确。

## “省略”也是协议设计

省略可选字段不是功能不完整，而是在事实边界上失败关闭。Iteration 0128 明确测试 OPML 没有 `dateCreated`、`dateModified` 和 HTTP Last-Modified，同时验证强 SHA-256 ETag、条件 GET、普通/条件 HEAD 和空 304。这样未来维护者不会为了“补字段”随手引入构建时间。

如果将来要增加日期，应先建立单一派生函数：综合根 Feed 表示修订、标签/专题索引成员变化和可审计的 OPML 格式修订时间，再证明生产边缘没有把日期或 ETag 语义破坏。字段的加入本身应作为公开缓存协议迁移独立迭代。

## 可复用经验

这个原则不只适用于 OPML。Sitemap、OpenSearch、JSON Schema、静态清单、生成 API 文档和下载包都可能面对相同问题：规范允许时间，不代表系统拥有时间事实。

选择元数据时先问三个问题：它描述什么对象、由哪些变化源决定、能否从事实源重复计算。答案不完整时，使用内容摘要表达身份，并省略无法证明的时间。少一个字段通常比多一个错误事实更可靠。
